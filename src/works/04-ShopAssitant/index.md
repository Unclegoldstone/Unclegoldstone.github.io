# 总体介绍

`ShopAssistant`是一款面向电商售后的客服智能体。商家可以使用其来回答客户的「查询物流」「查询订单」「查询相关政策」「询问商品信息」等常用问题。

比如客户提出「xxx商品在收到的时候已经破损了」, 该智能助手会自行询问关于该订单所缺失的信息，以整理成工单预览，等待客户确认后再创建工单， 以此减少无效工单的数量。

在回答「查询相关政策」相关问题时，助手会附带上相关政策的「原文引用」, 供用户直接查询相关条款。

遇到资料不足， 资料缺失，无法确认的问题时， 才将问题留给真人客服本身去审核回答， 在真人客服审核回答完成后， 会将回答的信息与问题作为新的知识， 为后续知识库的丰富来提供数据依据。

| 环节           | 所用技术                                                | 项目中的作用 |
| -------------- | ------------------------------------------------------- | ------------ |
| 工作流         | LangGraph、LangChain、ReAct、Function Calling           |              |
| 工具接入与执行 | 内置工具、MCP                                           |              |
| 多轮上下文管理 |                                                         |              |

| 观测与评估     | Langfuse                                                |              |



# 整体工作流

项目采用了 `Workflow 与 Agent 相结合` 的结构。订单确认、证据检查和建立工单等固定流程的事项， 由代码固化Workflow实现。 出现对话里需要通过用户的语义信息，以及查询信息来灵活决定下一步时，再交由Agent判断是否需要调用工具、是否需要向客户追问， 还是直接回答。下图展示了具体会划分为哪些分支， 笔者将会沿着各个分支， 介绍每一个意图类别是如何实现功能的。

## 商品查询

客户问「MH-W40 的水箱容量是多少？」时，消息会进入商品查询流程。系统先通过关键词和向量两路检索查找商品资料，再把候选资料合并、重排。这样既能匹配 `MH-W40` 这样的具体型号，也能处理「这款饮水机能装多少水？」这样的口语问法。

找到资料后，Workflow 会检查它是否足以回答当前问题。比如规格手册中明确写着 MH-W40 的水箱容量为 4 L，Agent 就可以根据这条资料作答，并附上可点击的原文引用。如果现有资料无法支撑结论，系统会提示暂时无法确认，并将问题记录下来，供后续审核和补充知识库。

<img src="assets\02-商品查询.png" style="zoom:50%;" >

## 退换货与售后

客户问「退货政策是什么？」时，系统会直接检索通用政策。如果客户问「订单 1001 可以退吗？」，系统会先确认并查询这笔订单，再根据订单信息查找适用条款。如果无法从对话里确定是哪笔订单，页面会请客户先选择订单，再继续处理原问题。

系统会检查找到的资料能否支撑当前问题。证据充足时，Agent 会结合订单信息和政策条款给出说明，并附上可点击的原文引用。证据不足时，系统会提示暂时无法确认，并将问题留待后续审核。

客户明确要求创建售后工单时，Agent 会先追问缺失的信息，再展示工单预览。客户确认后，系统才会创建工单。项目还提供模拟退款申请，客户主动提交后会生成一条待处理的演示记录。

<img src="assets\03-退货换货与售后.png" style="zoom:50%;" >

## 闲聊&投诉&意义不明

当客户打招呼、明确提出投诉，或一句话还不足以判断需求时，Workflow 会按识别出的主意图返回对应的预设回复。

- **闲聊**。像「你好」这样的问候，助手会简短回应，并引导客户说出遇到的具体问题。
- **投诉**。当客户说「我要投诉」，系统会回应客户的诉求，并提供「转人工」和「建工单」两个入口。演示环境会展示人工转接状态，工单则在客户确认后创建。
- **意图不明确**。如果客户只说「帮我处理一下」，而当前会话也没有足够信息，系统会请客户补充说明，再根据下一条消息判断该走哪条流程。

# Agent工具调用与MCP接入

简单说, Agent对于工具的使用就是， 每轮处理客户问题时，后端会把可用工具的名称、用途和参数定义交给 Agent，就像给它一份工具说明书。Agent 根据问题选工具、填参数。后端校验后，直接执行内置函数，或通过 MCP 请求独立服务。结果再交回 Agent，由它决定继续查询还是回复客户。

本项目提供了 `4个后端内置工具` 和 `3个通过MCP接入的工具`。具体工具的定义和用途如下.

## 定义的工具&功能

**内置工具**

| 工具            | 输入                                                 | 功能与实现                                                   |
| --------------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| `query_order`   | 订单号 `order_id`                                    | 从演示订单数据中读取商品摘要、订单状态、金额等信息。后端会核对订单是否属于当前用户。 |
| `query_product` | 商品关键词 `keyword`                                 | 生成演示商品名称、价格、库存和在售状态，用于展示商品信息查询的交互。 |
| `query_faq`     | 查询关键词 `keyword`                                 | 复用知识库检索服务，查找商品、政策和常见问题的相关片段。在常规政策问答流程中，Workflow 会先检索并检查证据，再交给 Agent 回答。 |
| `create_ticket` | 问题描述 `issue_description`、工单类型 `ticket_type` | 生成工单预览，等用户确认后写入 MySQL 的 `tickets` 表并返回工单号。同一次确认被重复提交时，系统复用已有结果。 |

**MCP工具**

| 工具                    | 所属服务 | 功能与实现                                                   |
| ----------------------- | -------- | ------------------------------------------------------------ |
| `query_logistics`       | 物流服务 | 按订单号返回模拟的承运商、运单号、配送状态和物流轨迹。       |
| `query_warranty`        | 售后服务 | 按订单号生成模拟保修状态，在保时返回剩余保修天数。           |
| `query_return_progress` | 售后服务 | 按订单号返回模拟退货进度，例如待寄回、仓库验收中或处理完成。 |

## 内置工具的实现

以`query_order`为例，以用户询问「订单 1001 买了什么？现在是什么状态？」为例，这次查询会经过四步。

**1. 把 Python 函数定义成 Agent 能调用的工具。** 使用 LangChain 的 `@tool` 为函数声明工具名和用途，用 Pydantic 定义参数。`query_order` 只需要一个参数 `order_id`，它是长度为 1 到 64 个字符的字符串。客服后端启动时，会把这个工具加入注册表。

```python
class OrderIdArgs(StrictToolArgs):
    order_id: str = Field(
        min_length=1,
        max_length=64,
        description="需要查询的订单号",
    )

@tool(
    "query_order",
    args_schema=OrderIdArgs,
    description="查询订单状态、金额和商品摘要。订单相关问题优先使用。",
)
async def query_order(order_id: str) -> dict[str, object]:
    return owned_order(order_id)
```

**2. Agent 把客户的话转换成工具调用。** Agent 根据工具描述选中 `query_order`，从问题中提取 `1001` 作为订单号，发出调用请求。

```python
{
  "name": "query_order",
  "args": { "order_id": "1001" }
}
```

**3. 后端校验参数并执行查询。** 执行器按工具名找到对应函数，检查订单号是否符合参数要求，再执行查询。演示订单在启动时从 `demo_orders.json` 读入，按订单号建立查询字典。函数找到 `1001` 后，会再用当前会话的用户 ID 核对订单归属。查询通过后返回订单字段。订单不存在或归属不符时，统一返回「未查询到相关信息」。

**4. 把结构化结果交回 Agent。** 执行器将查询结果包装成一条工具消息


## MCP工具的实现

由于该项目是一个演示项目， 且真实场景下， 物流轨迹、保修状态等的进度查询，都需要由商家或者承包业务的系统来提供。 故此项目使用两套MCP服务来模拟这些查询接口， 并让返回结果保留真实业务中常用的字段， 例如订单号、配送状态等。

**服务端: 生成模拟的物流数据**

我先在独立的物流服务中实现一个 Python 函数 `query_logistics(order_id: str)`。函数收到 `1001` 后，会把它作为这次查询的订单标识，从预设选项中生成承运商和配送状态，并生成一个以 `DEMO` 开头的运单号。物流轨迹使用「杭州揽收站 → 杭州转运中心 → 本地营业点」这组预设站点，再为每个站点配上相对当前时间的流转记录。

一次调用的返回结果可以是下面这样。这里节选了几个字段：

```python
{
  "order_id": "1001",
  "carrier": "顺丰速运",
  "tracking_no": "DEMO1234567890",
  "status": "派送中",
  "current_location": "本地营业点",
  "source": "demo"
}
```

写完生成逻辑后，我用 **FastMCP 的** `@server.tool()` 暴露这个函数。函数名成为工具名，文档字符串说明工具用途，`order_id: str` 用于生成输入参数定义。物流

**客户端: 发现并且调用服务**

当客户问「订单 1001 的快递到哪了？」时，客服后端先通过 `MultiServerMCPClient` 获取物流服务的工具列表。这个阶段读取的是**工具定义**，包括 `query_logistics` 的名称、用途和所需参数。后端确认该工具具备只读权限后，再把它提供给 Agent。

Agent 根据问题选择 `query_logistics`，并填入 `order_id="1001"`。客服后端收到这个调用请求后，会检查参数和订单归属。校验通过后，MCP 客户端才向物流服务发送 `tools/call`，传入工具名和订单号。



# 知识库的数据存储&匹配

## 数据如何存储

### 文档入库整体流程

客户问「拆封后还能退吗？」时，客服需要找到的不只是「7 天内可退」这句话，还包括条款里的适用条件和例外。为了让系统能找到这些内容，并在回答里引用出处，政策文件在进入知识库前要先整理。

下图展示了 ShopAssistant 的文档入库的总体流程。Word 和 PDF 资料先转换成 Markdown，已有的 Markdown 文件直接进入同一套处理流程。转换时保留标题、段落和表格，切片时沿用这些结构划分内容，并记录每个片段来自哪个章节。MySQL 保存片段原文及其来源，Milvus 为片段建立检索索引，两边通过片段 ID 关联起来。

<img src="assets\05-文档入库流程.png" style="zoom:50%;" >

### 不同格式文件的输入统一

这一步录入不同的文件，是需要一定手工操作的， 所用的工具在下方列出. 处理完统一成markdown后， 人工的步骤就结束了.

- Word(Docx) : 使用`Pandoc`把.docx转换为Markdown(该工具较方便， 下载安装后命令行内指定输入输出即可完成转换)。 转换后Word中的「标题 1」「标题 2」「标题 3」 会对应刀Markdown中的#、##、###。转换后需要人工审核常见出问题的遗漏项, 如`表格表头`, `标题对应的嵌套关系` 等是否和原文件一一对应。
- 文本型PDF : 使用`PyMuPDF`来提取文本块以及对应的页面坐标， 而后根据页面坐标来恢复文本本来的阅读顺序。
- 扫描件PDF : 使用`PaddleOCR`来完成文字识别和版面分析， 区分标题、正文、表格， 并且恢复阅读顺序。

**基本切片方法**

在完成文件格式的统一后， 因为LLM的上下文有限， 所以我们需要给文档切片， 具体怎么切也是有讲究的，如图所示为简单的`按句子切分`、`按照固定字数切分`、`按照段落切分`的结果以及可能的问题。

**本项目采用方法**

本项目对于文本的划分策略如下:

对于普通的文本， 形如: 

```markdown
#配送政策
##运费规则
普通商品订单实付金额满 99 元时免基础配送费；未满 99 元时收取 10 元基础配送费。偏远地区附加费、大件商品上楼费等特殊费用，以结算页展示为准。
[!IMPORTANT]
若订单拆分发货，基础配送费仍按整笔订单结算一次，不会按包裹重复收取。
##配送时效
现货商品通常会在付款后 48 小时内出库。预售商品以商品详情页标注的预计发货日期为准。
```

<img src="assets\08-知识切片实例2.png" style="zoom:50%;" >

**标题划分章节** : 系统先用 LangChain 的 `MarkdownHeaderTextSplitter` 读取标题层级。`# 配送政策` 是文档的一级标题，下面的 `## 运费规则` 和 `## 配送时效` 是两个并列的小节。系统据此把「满 99 元免基础配送费」和拆分发货的提醒归入 **「配送政策 → 运费规则」**，把「现货通常在付款后 48 小时内出库」归入 **「配送政策 → 配送时效」**。每个知识片段都会保留这条章节路径，便于检索后追溯出处。`[!IMPORTANT]` 会被识别为重要标记，提醒的正文仍保留在「运费规则」下。

<img src="assets\08-知识切片实例1.png" style="zoom:50%;" >

**正文按照句子组合** : 章节划分完成后，系统在各章节内按句号、分号等标点识别句子或分句，再按原文顺序组合。项目默认以 **1,000 字符**为切片长度目标。需要换片时，如果下一片还有空间，可以带上上一片末尾的完整句子或分句，默认重叠上限为 **120 字符**。以「运费规则」的首段为例，图中缩短了演示长度，让切分边界更明显。**片段 A** 包含「满 99 元免基础配送费」和「未满 99 元收取 10 元基础配送费」。**片段 B** 保留「未满 99 元收取 10 元基础配送费」这句，再接上偏远地区附加费等特殊费用的说明。两个片段共享的是一条完整的收费规则，因此即使只检索到其中一片，仍能读出这笔 10 元费用的适用条件。



对于表格类型的文本，如:

```markdown
| 问题类型 | 首次响应 | 处理时限   |
| -------- | -------- | ---------- |
| 退款     | 2 小时   | 3 个工作日 |
| 换货     | 2 小时   | 5 个工作日 |
| 维修     | 4 小时   | 7 个工作日 |
| 投诉     | 1 小时   | 3 个工作日 |
```

<img src="assets\08-知识切片实例3.png" style="zoom:50%;" >

系统先识别 Markdown 表格的表头和分隔行，再按原顺序把完整的数据行加入当前片段。如果加入下一行会超过长度目标，系统就在行与行之间切开，并把原表头和分隔行带到新片段。

图中使用 **128 字符**作为演示长度目标。片段 A 包含「退款」和「换货」，片段 B 包含「维修」和「投诉」，两片都保留原表头。这样，即使只检索到片段 B，也能直接读出维修的 **4 小时是首次响应时间，7 个工作日是处理时限**。

### 存储结构设计

本项目使用MySQL来存储切片后的数据， 使用Milvus来存储其对应的语义向量， 大体的存储设计如下.

| 存储                         | 核心字段                                                     | 用途                                           |
| ---------------------------- | ------------------------------------------------------------ | ---------------------------------------------- |
| **MySQL** `knowledge_chunks` | `id`（片段编号）、`answer`（片段正文）、`source_key`（来源标识）、`section_path`（章节路径）、`vector_status`（索引状态） | 保存可引用的正文和出处，记录索引是否建好。     |
| **Milvus**                   | `chunk_id`（对应 MySQL 的 `id`）、`text`（检索文本）、`dense_vector`（语义向量）、`sparse_vector`（BM25 稀疏向量） | 支持语义检索和关键词检索，返回命中片段的编号。 |

## 数据怎么匹配

以用户询问「维修一般多久能处理完？」为例，这张图展示了从 **Milvus 双路检索**到 **MySQL 取回正文、重排和证据检查**的全过程。下方的候选片段也说明了为什么回答引用的是「7 个工作日处理时限」，而不是「4 小时首次响应」。

<img src="assets\09-数据匹配.png" style="zoom:50%;" >

**BM25关键词检索** : BM25(Best Match 25), 负责做`字面上`的匹配， 其输入为具体的`关键词`, 输出为和此关键词对应的片段。

**向量检索** : 项目使用BGE-M3来生成每个片段的1024维的语义向量, 再通过Milvus按照`余弦相似匹配`来查找相关片段。负责做`语义上`的匹配。查询时， 将待查询语句转为语义向量， 再和Milvus中的向量匹配， 取top50。

**RRF融合** : RRF(Reciprocal Rank Fusion, 倒数排名融合), 把 `BM25` 和 `向量检索`所返回的候选结果合并成为一份最终排名。举例来说， 片段A, 在BM25中排名 (1 / 50), 在向量检索中排名 (3 / 40) 。 其得分计算公式为(1 / (k + 名次)), 也就是得分为 (1 /  51 + 1 / 43 ) ,  前2路检索中均检索到且排名靠前的会得高分往前排。

**BGE重排** : 将经由RRF排序后， 从MySQL中根据`chunk_id`取回的正文， 通过`bge-reranker-v2-m3`模型，根据问题与片段内容的相关性再次排序一次。 而后保留前10条相关数据。

**检查证据** : 本项目中， 把检查证据是否充分编写为一个独立的skill, 在Agent回答之前， 固定需要调用执行该skill。具体检查的项目为 : 1. 回答的是否为同一问题 2. 是否有直接支持结论的内容 3. 适用的条件是否明晰 4. 支持结论的材料是否一致 5. 证据是否可以追溯

# 数据飞轮

当出现助手回答不上的问题又或者出现客户给出负面反馈的回答时， 该条消息会被汇集到「知识改进」后台。维护者可以回看客户问了什么、当时找到了哪些资料，再决定是否需要补充知识。经人工核准的内容入库后，可以用原问题复测，确认这次补充是否解决了问题。
